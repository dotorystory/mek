# 2026-03-10 메일러 정상 발송 개선 방안 리포트

**작성일:** 2026-03-10  
**대상:** `home/plus/mailer/index.php`, `home/plus/mail_sender.php`  
**배경:** 다우오피스 IP Rate Control, Proofpoint 차단, 스팸 서버 오인 등으로 인한 수신 제한·실패 사례를 줄이고, 고객 메일이 원활히 전달되도록 메일러 측 조치 방안 정리.

## 0. 도메인·메일 서버 구성 (참고)

| 구분 | 호스트/도메인 | 메일 서버 |
|------|----------------|-----------|
| **메일 수신** | mekeng.com, (미확인: mail.mekeng.com) | **다우오피스** |
| **웹·메일 발송** | www.mekeng.com, webmail.mekeng.com | **이 서버** (발신 IP: 172.234.92.172) |

- 회사 메일 수신(수신함)은 **다우오피스**에서 처리하고, 홈페이지·문의 메일 발송은 **이 서버**(www.mekeng.com / webmail.mekeng.com)에서 처리합니다.
- 따라서 **@mekeng.com** 등으로 발송한 메일이 다우오피스 MX로 전달될 때, 발신 IP 172.234.92.172가 다우오피스 측에서 제한되면 수신 지연·실패가 발생합니다.

## 1. 배경 요약

- **다우오피스:** 발신 IP(172.234.92.172)에 대해 `421 Your IP is filtered by IP Rate Control` 적용 → 단시간 대량 발송 시 제한.
- **Proofpoint:** 동일 IP에 대해 `554 Blocked` → 수신측에서 스팸/위험 IP로 간주 가능.
- **메일러 현황:** 뉴스레터/직접입력/CSV/회원/구독자 대상으로 **수신자마다 연속 발송**, **발송 간격 없음**.  
→ 수신측에서 “짧은 시간에 같은 IP에서 다량 발송”으로 판단되어 Rate Limit·차단에 노출.

## 2. 메일러에서의 조치 방안

### 2.1 발송 간격(Throttling) 도입 **[우선 권장]**

**문제:** `index.php`의 `foreach ($emails as $email)` 루프에서 `send_mail_via_smtp()`를 **즉시 연속 호출**하여, 단시간에 많은 메일이 같은 IP에서 나감.

**방안:**  
- **수신자 1건 발송 후** 다음 수신자로 넘어가기 전에 **1~3초 sleep** 적용.  
- 예: `sleep(2);` (2초) 또는 설정값으로 분리 (예: 1초~3초, 다우/대형 메일서비스 완화 목적).

**효과:**  
- 다우오피스 “IP Rate Control” 완화에 직접 기여.  
- Proofpoint·삼성 등 “일시 제한(450)” 발생 가능성 감소.

**구현 위치:**  
- `home/plus/mailer/index.php` 발송 루프 내, `send_mail_via_smtp()` 호출 직후, 다음 수신자 처리 전.  
- **단,** “문의 메일 1건만 보내는 경우”에는 sleep 생략 또는 매우 짧게(0.5초 이하) 적용하는 옵션 권장 (사용자 체감 완화).

---

### 2.2 1회 발송 건수 제한 및 경고

**문제:** 한 번에 수백~수천 건 발송 가능하면, 수신측 Rate Limit·스팸 정책에 더 쉽게 걸림.

**방안:**  
- **1회 최대 발송 건수 상한** 도입 (예: 100건 또는 200건).  
  - 초과 시 “한 번에 N건까지 가능합니다. 나머지는 나누어 보내주세요.” 등 메시지로 차단.  
- 또는 상한을 넘을 경우 **“지연 발송 모드”**로 전환:  
  - 예: 50건 단위로 나누어 발송하고, 단위마다 1~2분 대기 후 다음 단위 발송 (구현 복잡도에 따라 선택).

**효과:**  
- 단시간 트래픽 폭주 방지 → 다우/Proofpoint 등에서 “대량 스팸”으로 보일 가능성 감소.

**구현 위치:**  
- `home/plus/mailer/index.php`에서 `$total_emails = count($emails);` 이후, 상한 초과 시 alert/redirect 및 발송 중단.

### 2.3 메일 헤더 보강 (스팸 오인 완화)

**문제:**  
- `mail_sender.php`의 PHPMailer 경로에서는 **Message-ID**, **List-Unsubscribe** 헤더를 설정하지 않음.  
- `send_mail_via_smtp_fallback()`(PHP `mail()`)에서는 **From/Reply-to, Content-Type**만 설정하고, **Message-ID·List-Unsubscribe** 없음.  
- 수신측 필터는 “정상 뉴스레터/트랜잭션 메일”일수록 Message-ID·List-Unsubscribe 있음을 선호함.

**방안:**  
1. **Message-ID**  
   - 형식: `\<고유문자열@도메인\>` (예: `\<메시지고유값@smtp발신도메인 또는 mekeng.com\>`).  
   - PHPMailer 사용 시: `$mail->MessageID = ...` 또는 `addCustomHeader('Message-ID', ...)` (PHPMailer 버전에 따라 상이).  
   - Fallback(`mail()`) 사용 시: `$headers`에 `Message-ID: ...` 추가.  

2. **List-Unsubscribe**  
   - 뉴스레터 발송 시 구독 취소 URL을 **헤더**에도 포함.  
   - 예: `List-Unsubscribe: <https://도메인/plus/mailer/?action=unsubscribe&key=...&email=...>`  
   - 필요 시 `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) 추가 시 일부 클라이언트에서 원클릭 구독 취소 지원.  
   - PHPMailer: `addCustomHeader('List-Unsubscribe', ...)`.  
   - Fallback: `$headers .= 'List-Unsubscribe: ...' . "\r\n";`  
   - 단, **문의 메일(1건)** 등 뉴스레터가 아닌 경우에는 List-Unsubscribe 생략 가능.

3. **X-Mailer / 발신 앱 식별**  
   - 예: `X-Mailer: MEK-WebMailer/1.0` 등으로 고정.  
   - 수신측에서 “알 수 없는 클라이언트”로 보이지 않게 하는 데 도움.

**효과:**  
- 스팸 필터에서 “정상적인 뉴스레터/비즈니스 메일”로 분류될 가능성 향상.  
- Proofpoint 등에서 “정당한 발신”으로 보이도록 하는 데 기여.

**구현 위치:**  
- `home/plus/mail_sender.php`:  
  - `send_mail_via_smtp()` 내 PHPMailer 설정 구간에서 Message-ID, List-Unsubscribe(뉴스레터일 때), X-Mailer 추가.  
  - `send_mail_via_smtp_fallback()` 내에서 동일 헤더를 `$headers`에 추가.  
- 구독 취소 URL은 이미 `generate_unsubscribe_key`, `action=unsubscribe` 등으로 생성 가능하므로, 그 값을 헤더에만 넘기면 됨.

### 2.4 도메인 인증(SPF/DKIM/DMARC) — 인프라 권장

**문제:**  
- 발신 IP(172.234.92.172)가 **mekeng.com** 도메인으로 메일을 보낼 때, 수신측에서 “이 IP가 해당 도메인 발신을 허용받은 IP인가?”를 SPF/DKIM/DMARC로 검사.  
- 설정이 없거나 잘못되면 스팸·피싱으로 오인되기 쉬움.

**방안:**  
- **SPF:** mekeng.com DNS에 `v=spf1 ip4:172.234.92.172 ... include:... ~all` 등으로 발신 서버 IP 포함.  
- **DKIM:** 발신 서버(또는 중간 릴레이)에서 서명을 붙이고, 도메인 DNS에 공개키 등록.  
- **DMARC:** 도메인 정책 레코드로 “SPF/DKIM 실패 시 어떻게 할지” 명시.  

**효과:**  
- “정식 도메인에서 보낸 메일”로 인정받아 스팸함·차단 가능성 감소.  
- Proofpoint 등에서 발신자 신뢰도 향상에 기여.

**구현:**  
- **메일러 코드 변경이 아니라**, 서버/DNS 관리 측 작업.  
- 메일러는 “동일 From/도메인·동일 발신 경로”를 유지하면 됨.

### 2.5 반송(NDR)·실패 주소 관리

**문제:**  
- 알 수 없는 사용자(550/505 등)로 반송된 주소를 계속 수신 대상에 넣으면, 수신측에 “잘못된 주소로 반복 발송”으로 기록되어 발신 IP/도메인 평판이 나빠질 수 있음.

**방안:**  
- 발송 로그(`g5_mail_send_log` 등)에 **실패 사유**가 저장되어 있다면,  
  - “User unknown” 등 **영구 실패**로 분류된 주소는 **다음 발송 시 자동 제외**하거나,  
  - 관리자 화면에서 “반송/실패 주소 목록”을 보여 주고 수동 제거.  
- 구독자/회원/CSV 대상 발송 시, 해당 이메일을 **일시 비활성** 또는 **반송 플래그**로 표시하는 정책 도입 검토.

**효과:**  
- 불필요한 재발송 감소 → 수신측 불만·블랙리스트 가능성 감소.

**구현 위치:**  
- 로그 조회·필터 기능이 있는 `index.php` 또는 전용 관리 화면.  
- 발송 루프에서 “이전 발송 실패(영구 실패)” 목록을 조회해 제외하는 로직 추가.

### 2.6 문의 메일(1건) vs 뉴스레터(대량) 분리

**문제:**  
- 홈페이지 문의는 **1건 즉시 발송**이 중요하고,  
- 뉴스레터는 **대량·지연 발송**이 필요함.  
- 같은 발송 경로를 쓰더라도, **동작 정책만 분리**하면 사용자 경험과 수신 제한 완화를 동시에 만족시키기 쉬움.

**방안:**  
- **문의/알림 등 1건 발송:**  
  - sleep 없음 또는 매우 짧은 대기.  
  - 1회 발송 건수 제한에서 제외.  
- **뉴스레터(직접입력/CSV/회원/구독자 다수):**  
  - 수신자당 1~3초 sleep 적용.  
  - 1회 최대 N건 제한 적용.  
- 현재 메일러가 “뉴스레터 발송” 전용이면, **모든 발송에 sleep + 상한**을 적용하고,  
  - 나중에 “문의 1건” 전용 엔드포인트가 생기면 그쪽만 sleep 미적용으로 두면 됨.

## 3. 우선순위 요약

| 순위 | 조치 | 효과 | 구현 난이도 |
|------|------|------|-------------|
| 1 | 발송 간격(sleep) 도입 | 다우/Proofpoint 등 Rate Limit 완화에 직접 기여 | 낮음 |
| 2 | 1회 발송 건수 상한 | 단시간 대량 트래픽 방지 | 낮음 |
| 3 | Message-ID / List-Unsubscribe 헤더 | 스팸 오인 완화, 정상 뉴스레터로 인정받기 쉬움 | 중간 |
| 4 | SPF/DKIM/DMARC (인프라) | 도메인·발신 IP 신뢰도 향상 | 서버/DNS 담당 |
| 5 | 주소 없음, 반송 주소 자동 제외/관리 | 반복 실패·평판 하락 방지 | 중간 |
| 6 | 문의 1건 vs 뉴스레터 분리 | UX + Rate Limit 대응 동시 만족 | 낮음(정책 분기만) |

## 4. 정리

- **메일 수신 제한·스팸 서버 오인**을 줄이려면,  
  1) **발송 속도 완화(Throttling + 1회 상한)**  
  2) **정상 메일로 보이게 하는 헤더(Message-ID, List-Unsubscribe)**  
  3) **도메인 인증(SPF/DKIM/DMARC)**  
  이 세 축을 함께 적용하는 것이 좋습니다.  
- 메일러 코드 상에서는 **2.1 발송 간격**, **2.2 1회 건수 제한**, **2.3 헤더 보강**을 먼저 적용하고,  
  인프라 측에서 **2.4 SPF/DKIM/DMARC**를 점검·보완하면,  
  다우오피스 문의(`2026-02-23_다우오피스_메일수신제한_문의.md`)와 함께 **정상적인 고객 메일 발송**이 더 원활해질 것으로 예상됩니다.
